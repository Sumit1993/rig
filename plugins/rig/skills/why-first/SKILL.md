# Why first

Before building something new, check whether others have already solved it. Then learn why their answer exists before copying what it does. A list of features tells you what they built, not whether you need it.

Write the note in this order:

1. **Why.** What forces made the standard what it is: scale, volume, new kinds of users or authors, cost, trust, failure. Number each force, and give each one a number and a source.
2. **What.** What the standard does. Tie each part to the force it answers. List a part no force explains as unexplained.
3. **Reception.** How users received it: praise, complaints and reversals.
4. **Implications for us.** Last. Tie each one to a force. Turn each into a change we make, or reject it in one line with the reason.

A note that only lists features is incomplete.

Keep the scope tight:
- Research each subject once. Reuse an existing note.
- Sweep every subject the work touches up front. Do not wait to be pointed at each one.
- Hand the research to a subagent: Opus at medium effort, with web search. It returns the note as text.
- Keep a note to 100 lines or fewer.
- Mark what you could not confirm, and say where you looked.
- Skip the research for a pure fix, or for a follow-up on a subject that already has a note.

Do not adopt the reference's persona. The bar is to be as good as or better than what the user would otherwise use, not to become it. Nothing you post names a product or links into `~/ai-context`: write "reference A, B, C". Never paste the research into a PR. A PR names the change and the force it answers.

This is how `AGENTS.md`'s "a question with an outside answer gets it read" is done. It applies to the planner seat, to `farm-out` work orders and to the survey in `hill-climb`.
